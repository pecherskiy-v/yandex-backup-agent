# Яндекс.Диск как место хранения резервных копий

Кастомная интеграция: после установки Диск появляется в
**Настройки → Система → Резервные копии** наравне с локальным хранилищем —
отдельной кнопки и ручного копирования не нужно.

## Зачем, если есть WebDAV

У Диска есть WebDAV, и HA умеет с ним работать «из коробки», но большие
файлы через него не уезжают: сервер принимает тело PUT, не отвечает, и
соединение висит, пока не умрёт по таймауту. В журнале это выглядит как
`Backup operation failed: No connection with https://webdav.yandex.ru`, хотя
связь есть и мелкие запросы проходят.

Заодно чинится и вторая беда ручного подключения — протухающий токен.
Штатный OAuth Home Assistant тут не годится: он возвращает браузер на
`my.home-assistant.io`, а Яндекс разрешает в Redirect URI только
подтверждённые домены и не даёт менять адрес даже при создании приложения.
Поэтому используется код подтверждения: в отличие от токена из адресной
строки, его обмен даёт ещё и refresh-токен, а значит доступ продлевается
сам.

REST API устроен иначе: сначала берётся одноразовая ссылка на загрузку,
и файл льётся на storage-узел — тем же путём, что у родного клиента Диска.
Размер уходит заголовком `Content-Length`, так что тело не режется на
chunked, на котором Диск и спотыкается.

## 1. Завести приложение Яндекса

Один раз, в браузере. Пароль от Яндекса ни Home Assistant, ни этот код не
видят: приложению выдаётся доступ, а не учётная запись.

1. Открыть <https://oauth.yandex.ru/client/new/>.
2. Платформа — «Веб-сервисы». **Redirect URI Яндекс подставляет сам**
   (`https://oauth.yandex.ru/verification_code`) и менять его не даёт —
   так и надо, интеграция рассчитана именно на него.
3. Доступы, раздел «Яндекс.Диск REST API»:
   `cloud_api:disk.read`, `cloud_api:disk.write`, `cloud_api:disk.info`.
4. Сохранить и запомнить **ClientID** и **секрет приложения**.

## 2. Поставить компонент

### Через HACS

HACS → три точки → «Custom repositories» → вставить `https://github.com/pecherskiy-v/yandex-backup-agent`,
категория «Integration» → установить → перезапустить HA.

### Руками

Скопировать каталог в конфиг HA и перезапустить:

```
<config>/custom_components/yandex_disk_backup/
```

## 3. Подключить

**Настройки → Устройства и службы → Добавить интеграцию → «Яндекс.Диск
(копии)»**, дальше три коротких шага:

1. ClientID и секрет приложения;
2. ссылка на страницу разрешения — нажать «Разрешить» и вставить обратно
   короткий код подтверждения, который Яндекс покажет на экране;
3. папка (по умолчанию `Home Assistant/backups`) — создаётся сама, вместе
   с родительскими.

Код вводится **один раз**: интеграция меняет его на пару токенов и дальше
продлевает доступ сама.

Папку потом можно сменить кнопкой «Настроить» у интеграции. Уже загруженные
копии при этом остаются лежать на старом месте — переносить или нет, решает
владелец.

После подключения в разделе резервных копий появится место хранения
`Яндекс.Диск · <логин>`: его можно отметить в расписании, и копии поедут
туда автоматически.

## Как оно лежит на Диске

Рядом с каждым архивом лежит файл метаданных с тем же именем — раскладка
та же, что у штатного агента WebDAV:

```
Home Assistant/backups/
  Automatic_backup_2026.9.2.tar
  Automatic_backup_2026.9.2.metadata.json
```

Список копий строится по метаданным: в них есть всё, что показывает
интерфейс, и качать ради этого гигабайтный архив не нужно. Метаданные
пишутся **после** архива — значит, копия без метаданных не доехала, и в
списке она не появится. Огрызок такой копии остаётся на Диске: удалять его
нужно руками, зато HA никогда не предложит восстановиться из обрезанного
архива.

Удаление идёт мимо корзины: корзина Диска считается в тот же объём, и
«удалённые» копии продолжали бы занимать место.

## Грабли

- **Доступ не протухает сам по себе.** Интеграция хранит refresh-токен и
  продлевает доступ за час до истечения — в том числе посреди долгой
  загрузки. Руками токен не выпускают и не продлевают. Если доступ отозвали
  в настройках Яндекса, интеграция уходит в ошибку и просит новый код;
  приложение, папка и расписание при этом сохраняются.
- **Код подтверждения одноразовый и живёт недолго.** Если между «Разрешить»
  и вставкой прошло много времени, Яндекс ответит `invalid_grant` — надо
  просто взять новый код по той же ссылке.
- **Свободное место.** Полный бэкап HA — сотни мегабайт, а бесплатный Диск
  это 10 ГБ. Ретеншен (сколько копий хранить) задаётся в самом HA, в
  настройках расписания, отдельно для каждого места хранения.
- **Скорость.** Диск не обещает быстрой отдачи; первая копия на 300 МБ может
  ехать несколько минут. Таймаут на загрузку — 12 часов, обрыв связи
  агент честно покажет ошибкой, а не молчанием.
- **Копия без базы.** Если гонять копии часто, стоит выключить в расписании
  включение базы рекордера — она и есть основной вес архива.

## Дозалить копию, которая уже есть

Кнопка «Загрузить в другое место» в Home Assistant 2026.9 ведёт через приём
файла Supervisor'ом и падает на его собственном баге
(`hassio/backup.py`, `KeyError: '.cloud_backup'`) — куда бы копию ни
отправляли. Поэтому здесь есть свой сервис: он берёт поток у места
хранения-источника и сразу отдаёт его Диску, ничего не выгружая наружу.

**Инструменты для разработчика → Действия → «Залить копию на Диск»**, или
в YAML:

```yaml
action: yandex_disk_backup.upload_existing
data:
  backup_id: 4bcc4ff2          # из раздела резервных копий
  source_agent_id: hassio.local # по умолчанию локальное хранилище
```

Ход видно в журнале: по строке на начало и конец каждой копии. Когда в HA
починят приём файла, надобность отпадёт — сервис останется для сценариев.

## Иконка

Картинка рисуется кодом — `brand/make_icon.py`, облако со стрелкой вверх на
синем поле. Логотип Яндекса намеренно не используется: чужой товарный знак.

В карточке HACS иконка берётся из корня репозитория (`icon.png`, `logo.png`).
А вот в списке интеграций Home Assistant тянет её из
[home-assistant/brands](https://github.com/home-assistant/brands) и для
кастомных доменов ничего не находит — вместо значка будет заглушка. Чтобы
появилась своя, нужен PR в brands: готовый набор лежит в
`brand/custom_integrations/yandex_disk_backup/` (icon, icon@2x, logo,
logo@2x) — его кладут ровно в такой же путь в форке brands.

## Версии

HACS показывает версию по **GitHub Releases**, а не по тегам: без релиза в
карточке будет хеш коммита вместо номера. Руками это делать не нужно —
выпуск повешен на тег:

```bash
# поднять version в custom_components/yandex_disk_backup/manifest.json,
# закоммитить, затем:
git tag v3.1.0 && git push origin v3.1.0
```

Дальше `.github/workflows/release.yml` сам соберёт заметки из коммитов и
опубликует релиз. Он же сверяет версию в `manifest.json` с тегом и падает,
если они разъехались: молча поставить одно, а показывать другое — хуже, чем
не выпустить вовсе.

Отдельно `.github/workflows/validate.yml` гоняет тесты, проверку HACS и
hassfest — на каждый пуш и раз в неделю по расписанию, потому что
требования HACS меняются сами по себе.
